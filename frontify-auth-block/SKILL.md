# Frontify Auth — Custom Blocks

Custom Blocks are React components that an editor places onto a Brand
Guideline page. Like Apps, they run **inside** the Frontify Platform under
the AppBridge — there is no token to manage and no OAuth dance to
implement. The host injects an authenticated session and a typed block
context (the surrounding guideline, brand, and any asset references the
editor wired up).

The auth surface for a Custom Block developer is small:

1. **AppBridge** — connects the block to the host's session
2. **Block context** — the brand / guideline / page / asset references the
   block can act on
3. **Implicit scope** — a block runs in the *viewing user's* permission
   context; there is no separate scope manifest to declare for blocks
4. **External HTTP** — a block can `fetch()` directly from its iframe; for
   secrets, use a server-side proxy (blocks have no built-in secure-request
   equivalent of `executeSecureRequest`)

If the user is building a **Frontify App** (asset action, asset creation,
workspace, …), stop and load `../frontify-auth-app/SKILL.md` — Apps have a
richer auth surface (`executeSecureRequest`, manifest scopes/secrets). If
the work is **outside** the platform entirely, load
`../frontify-auth-integration/SKILL.md`.

## Quick reference

### 1 — Block AppBridge

A Custom Block uses the Brand SDK's block bridge. Construction is
synchronous; the bridge connects the moment the block is instantiated by
the host:

```ts
import { useBlockSettings, useEditorState, useBlockAssets } from '@frontify/app-bridge';
// (exact hooks and exports follow the @frontify/app-bridge package the
// scaffolded block uses — verify against the project's package.json)
```

The block scaffolding generated by `npx @frontify/frontify-cli@latest create`
wires this up automatically. There is no manual `new AppBridge…()` call to
write.

### 2 — Block context

Blocks receive their surface context as React props/hooks:

| Concept | Purpose |
|---------|---------|
| **Block ID** | Stable identifier for this block instance within the page |
| **Brand / Guideline / Project IDs** | Where the block is rendered — drives any "scope to current brand" logic |
| **`isEditing`** | Boolean — true when the editor is in edit mode, false in view mode |
| **Asset references** | Assets the editor selected for this block, exposed via the asset chooser settings |
| **Color references** | Color tokens the editor selected for this block |
| **Block settings** | Editor-configured values declared in the block's settings schema |

The exact hook names depend on the SDK version; cross-check
`node_modules/@frontify/app-bridge/dist` or the block scaffolding's
`src/index.tsx`. The auth-relevant fact is that **all of these arrive
already authenticated** — the block doesn't need to negotiate identity.

### 3 — Calling Frontify GraphQL from a block

Blocks call GraphQL via the AppBridge, the same pattern as Apps. The block
never sees a token; the host injects it server-side. After the call returns,
treat the response just like any GraphQL response (data + errors).

```ts
const { data } = await appBridge.executeGraphqlRequest({
  query: /* GraphQL */ `
    query {
      currentUser { id email }
    }
  `,
});
```

The exact method name depends on the SDK version (`appBridge.api({...})`,
`appBridge.executeGraphQlRequest({...})`, or `useBlockApi` hook style).
Verify in the scaffold output — the auth-relevant fact is that **all
GraphQL calls go through the bridge, never via direct `fetch` to
`/graphql`**.

For data work, also load `../frontify-graphql/SKILL.md`.

### 4 — Calling third-party APIs from a block

Custom Blocks **do not** have an `executeSecureRequest` equivalent. The
block can issue normal browser `fetch()` calls from its iframe — but
anything in the call (URL, headers, body) is visible to the user's browser.
That means:

- **OK to call** public, no-auth endpoints (e.g. open data, RSS, public
  CMS read APIs)
- **OK to call** endpoints that authenticate via cookies the user already
  has (e.g. the user's own SSO session against the same domain)
- **Not OK** to embed an API key, bearer token, or any other shared secret
  in the block bundle — it ends up in the user's devtools

For credentialed third-party calls, the **only safe pattern** is a
server-side proxy:

1. Stand up a small backend service that holds the credential
2. Block `fetch()`s that backend, passing only non-sensitive parameters
3. Backend authenticates against the third party server-to-server, returns
   results to the block

If the secret needs to live alongside Frontify rather than your own
infrastructure, the user should build a **Frontify App** instead of a
Custom Block — Apps have `executeSecureRequest` and Marketplace-stored
secrets. Load `../frontify-auth-app/SKILL.md` for that path.

### 5 — Implicit scope and permissions

Custom Blocks **do not** declare scopes in a manifest. The block runs in
whatever permission context the **viewing or editing user** has — there is
no separate "block identity."

What this means in practice:

| Mode | What works | What doesn't |
|------|------------|--------------|
| Editor in edit mode | Anything an editor can do (configure settings, attach assets, save) | Anything the editor's account isn't permitted to do |
| Editor in view mode | Same data access as edit mode, but the block UI typically hides write controls | n/a |
| Viewer | Read paths the viewer is allowed | Write paths (settings save, asset uploads) — the host blocks these UI-side |

The block should:

- **Branch on `isEditing`** to show editor-only controls
- **Check entity-level `currentUserPermissions`** in GraphQL responses
  before rendering write affordances (e.g. don't show a "Replace asset"
  button if `canEdit` is false on the asset)
- **Treat 403s as "user can't do this"**, not auth failure — refreshing
  won't help

Detailed scope/permission notes in `references/scopes-and-permissions.md`.

### 6 — Settings vs. secrets

Block settings are declared in the block's settings schema (typically with
`@frontify/guideline-blocks-settings`). They are admin-/editor-configured
and visible to anyone who can view the block's source.

**Don't put secrets in block settings.** They appear in the rendered iframe
and travel with the page. If a credential is needed, proxy via your own
backend (above).

### 7 — Lifecycle

When a viewer or editor opens a guideline page:

1. Frontify renders each block in its own iframe with the host context
   pre-populated
2. The bridge is connected synchronously — no async login
3. Block state subscribes to changes (settings updates, asset re-selections,
   editor → view mode transitions)
4. Closing the page tears down the iframe — persist anything important via
   block settings or AppBridge state before then

There is no token refresh, no expiry, no reconnection. The auth surface for
a block is intentionally narrow.
