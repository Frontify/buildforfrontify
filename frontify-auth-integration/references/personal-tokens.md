# Personal Developer Tokens & Service-User Tokens

A personal developer token is a static bearer token tied to a Frontify user.
It skips the OAuth 2 dance, which makes it useful for:

- **Local development** and testing
- **CI/CD pipelines** (GitHub Actions, GitLab CI, Jenkins, etc.)
- **Setting up a Service App** — the `createServiceApp` GraphQL mutation
  requires a user session, so you generate a token, run the mutation, then
  switch to client-credentials at runtime
- One-shot scripts, manual data backfills, ad-hoc admin tasks

> **Personal tokens are not recommended for production user-facing
> integrations.** Use a Service App (machine-to-machine) or OAuth 2 Client
> (user-delegated) for those.

## Generating a token

1. Sign in to the target Frontify instance as the user the token should
   represent.
2. Navigate **directly** to `https://<your-domain>/oauth-access-token`. This
   page is **not linked from the UI** — there is no profile menu, top-right
   icon, or navigation entry that takes you there. You must enter the URL
   by hand. (Older docs reference a profile / Applications area; that
   entry no longer exists.)
3. Click **+ Create token**.
4. Fill in:
   - **Name** — meaningful identifier; appears in the listing UI for
     audit/revoke later
   - **Description** — what this token is used for and where (e.g. "GitHub
     Actions: nightly asset sync")
   - **Scopes** — the OAuth scopes this token will carry. **Cannot be
     changed after creation** — if scopes change later, generate a new token
     and revoke the old one
   - **Expiration** — one of: `7 days`, `30 days`, `90 days`, `6 months`,
     `1 year`
5. Click **Create**. The token string is shown **once** — copy it now.

Token strings look like:

```
cmFCUDPvYxaGgFN6aLBtfr7659Hp2AP8hW8ik77Q2mru4
```

> **Tokens issued before January 2026 have a 10-year expiry.** New tokens
> are capped at 1 year. Build rotation into the integration from day one.

## Using the token

Same pattern as any Frontify bearer token:

```bash
curl -H "Authorization: Bearer cmFCUDPv...mru4" \
  -H "Content-Type: application/json" \
  -d '{"query":"{ currentUser { id email } }"}' \
  https://{domain}/graphql
```

Permissions resolve against the user the token was generated by. If that
user is a Viewer on a library, the token cannot edit assets in it — even if
the token has `basic:write` scope.

## Service-user pattern (recommended for long-lived integrations)

Tying a production integration to a real human user is brittle: when they
leave the organisation and their account is deleted, **the token dies and
cannot be recovered.** Frontify Customer Support cannot restore lost
service-user credentials.

The recommended pattern:

1. **Provision a dedicated email** — e.g.
   `integration-name@yourcompany.com` (a real mailbox or an alias to a
   shared inbox).
2. **Invite the user to Frontify** with that email.
3. **Complete signup**. Use a name like `DO NOT DELETE - Integration-name
   user` so admins recognize it as critical infrastructure.
4. **Grant project / library permissions** appropriate for the integration.
   Apply least-privilege — only the libraries / projects the integration
   touches.
5. **Sign in as the service user** and generate the token at
   `/oauth-access-token`.
6. **Document** somewhere durable (runbook, secrets manager) which token
   maps to which integration and when it expires.

This same service user can also own a **Service App** (client credentials),
which is preferable to a long-lived personal token for production. The
personal token is then only used to bootstrap the Service App.

## Rotation

There is no automated rotation. Plan rotation explicitly:

- Set a calendar reminder one week before expiry
- Generate the new token first; deploy it; then revoke the old one
- For multi-environment deploys (dev / staging / prod), rotate per-env on a
  staggered schedule

## Revocation

Open the same `/oauth-access-token` page (signed in as the user who owns the
token). Each token row has a **Revoke token** button. Use it when:

- The token has been replaced and you're confident the old one is unused
- The token is suspected leaked
- The integration is decommissioned
- The owning user is leaving and their tokens need to be replaced before
  account deletion

## CI/CD checklist

- Store the token in the platform's secret store (GitHub Encrypted Secrets,
  GitLab CI Variables masked, etc.) — never commit it
- Inject as an env var at job runtime; never log the value
- Use a service-user token, not a real engineer's
- Set `Authorization: Bearer ${FRONTIFY_TOKEN}` in the request, not in the
  URL
- Add a smoke-test step (`{ currentUser { id } }`) before the workflow
  starts mutating data — fast-fail on auth issues

## Limits

A given personal token is bound to a single Frontify account. Multi-account
integrations need either multiple tokens (one per account) or coordination
with `developer@frontify.com`.
