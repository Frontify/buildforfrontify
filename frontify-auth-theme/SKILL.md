# Frontify Auth — Themes

A Frontify Theme controls the visual appearance of one or more Brand
Guidelines and can expose actions on the Guidelines surface. Like Apps and
Custom Blocks, Themes run **inside** the Frontify Platform — the host
injects the user's session through the AppBridge, and the theme inherits
the surrounding Portal / Project / Brand context.

The auth surface for a Theme developer is intentionally small:

1. **AppBridge** — connects the theme to the host's session
2. **Theme context** — the Portal, Project, Brand the theme is rendering
   for, plus per-action context (e.g. `themeAction` Alpha surface)
3. **Implicit scope** — themes don't declare scopes; rendering happens in
   the **viewing user's** permission context
4. **External HTTP** — like blocks, themes can `fetch()` directly from
   their iframe; for credentialed third-party calls, proxy via your own
   backend (themes have no `executeSecureRequest` equivalent)

If the user is building a **Frontify App** (asset action, asset creation,
workspace, page action, …), stop and load `../frontify-auth-app/SKILL.md`
— Apps have a richer auth surface (manifest scopes/secrets,
`executeSecureRequest`). For external integrations, load
`../frontify-auth-integration/SKILL.md`.

## When to use this skill

Load this skill when the user is building a Theme and:

- Wants to read or mutate Frontify data from inside the theme
- Needs the current user's identity, the surrounding Portal/Project/Brand,
  or the asset/page references the theme is rendering
- Is building a `themeAction` (Alpha) surface that needs context or auth
- Calling a third-party API from a theme iframe
- Encounters a 401 / 403 / silent empty response in a theme
- Is wondering why a theme can do X for an editor but not for a viewer

Do **not** load this skill for Apps, Custom Blocks, or external
integrations.

## Quick reference

### 1 — Theme AppBridge

A Theme uses the Brand SDK's theme bridge. The scaffolding generated by
`npx @frontify/frontify-cli@latest create` wires it up. There is no
manual login — the bridge connects synchronously and the user's session is
already authenticated when the theme renders.

```tsx
import { type ThemeProps } from '@frontify/guideline-blocks-settings';
// (the exact entry-point shape depends on the SDK version the scaffold
// emits — verify against the project's package.json and src/index.tsx)

export const MyTheme = ({ appBridge }: ThemeProps) => {
  // appBridge is connected; no async login step
};
```

### 2 — Theme context

A Theme renders against three levels of identity:

| Concept | Purpose |
|---------|---------|
| **Brand** | Which brand's guidelines the theme is currently styling |
| **Project** | The guideline project (one brand can have many) |
| **Portal** | The published guideline surface (`portalId` on `themeAction`) |
| **`isEditing`** | True in edit mode, false in view mode — drives editor-only UI |
| **Page / section ID** | Available on per-page or per-section themes |

These are not auth tokens, but they're how the theme knows where it lives.
Use them to scope queries and to construct deep links.

### 3 — `themeAction` surface (Alpha)

Themes can expose an action button on a Guideline page. When the user
clicks it, Frontify launches the theme's action handler with this context:

```ts
type ThemeActionContext = {
  surface: 'themeAction';
  portalId: string;
  projectId: string;
} & AppBaseProps;
```

Where `AppBaseProps` is the common app shape:

```ts
type AppBaseProps = {
  brandId: number;
  domain: string;
  parentId: string;
  rootId: string;
};
```

The user is already authenticated when the action fires. Use the surface
ID to branch logic on the action vs. normal rendering paths. See
`references/surfaces-and-context.md` for the full per-surface table.

### 4 — Calling Frontify GraphQL from a theme

Themes call GraphQL via the AppBridge — no token to set, no
`Authorization` header to manage:

```ts
const { data } = await appBridge.executeGraphqlRequest({
  query: /* GraphQL */ `
    query CurrentBrand($brandId: ID!) {
      brand(id: $brandId) {
        id
        name
        guidelines { items { id name } }
      }
    }
  `,
  variables: { brandId },
});
```

The exact method name follows the SDK version (`appBridge.api({ name:
'executeGraphql', payload: {...} })` or `executeGraphqlRequest`). Verify in
the scaffold output. **Do not** call `https://<domain>/graphql` directly
with `fetch` — there's no token to put in the header and you'd be
side-stepping the host.

For data work, also load `../frontify-graphql/SKILL.md`.

### 5 — Calling third-party APIs from a theme

Themes have **no `executeSecureRequest` equivalent.** A theme runs in the
user's iframe; anything in a `fetch()` call is visible in DevTools.

What's safe:

- **Public, no-auth endpoints** (open data, public CMS read APIs)
- **Endpoints authenticated via cookies the user already has** (same root
  domain, SSO session)

What's not safe:

- **Embedding API keys or bearer tokens in the theme bundle** — they leak
  to every guideline viewer

For credentialed third-party calls, proxy via your own backend (the same
pattern as Custom Blocks — see `../frontify-auth-block/references/external-calls.md`
for the full proxy walkthrough; the design is identical for themes). If
the secret needs to live alongside Frontify rather than your own
infrastructure, the user should build a **Frontify App** instead — Apps
have `executeSecureRequest` and Marketplace-stored secrets.

### 6 — Implicit scope and permissions

Themes **do not** declare scopes in a manifest. The theme runs in whatever
permission context the **viewing or editing user** has — there is no
separate "theme identity."

This means:

| Mode | What works | What doesn't |
|------|------------|--------------|
| Editor in edit mode | Anything the editor's account permits (configure theme settings, attach assets) | Anything the editor's account doesn't permit |
| Editor in view mode | Same data access as edit mode; write controls hidden | n/a |
| Viewer | Read paths the viewer is allowed | Write paths — the host blocks them UI-side |

The theme should:

- **Branch on `isEditing`** to show editor-only controls
- **Check entity-level `currentUserPermissions`** before rendering write
  affordances
- **Treat 403s as "user can't do this"**, not auth failure — refresh won't
  help

### 7 — Lifecycle

When a viewer or editor opens a guideline:

1. Frontify mounts the theme with the surrounding context pre-populated
2. The bridge is connected synchronously
3. The theme subscribes to state changes (settings updates,
   editor → view mode transitions)
4. Closing the guideline tears down the iframe — persist state via theme
   settings or AppBridge state stores

There is no token refresh, no expiry. The theme's auth surface is narrow.
